# 设计师评审说明：动态剧情分支实验

## 这份材料要回答什么

本实验用于判断：玩家做出的少量选择，能否通过人物目标、人物关系和世界规则，持续影响多个角色与后续事件；以及这种做法是否比给每个角色预写大量独立剧情分支更适合作为项目的设计参考。

它是工程可行性样例，不是可玩性 Demo。界面只强调三件事：**能做的选择、选择后的结果、结果是否符合预期**。游戏词汇用于包装规则，界面按步骤展开，避免把所有信息平铺在同一屏。

## 实验模型

- 50 名选手、10 支战队，记录所有 1,225 组人物关系。
- 推演跨度为 5 个赛季；每季都可以改变阵容、训练、双排或观察。
- 人物带有职业目标、野心、士气、忠诚、队长或导师身份；事件规则会根据状态和关系触发。
- 可检查的剧情包括默契搭档、首发竞争、替补转会、转会受阻、队内摩擦和队友带练。
- 赛果记录触发前提、人物动机、结果以及已写入的前因事件，支持复跑和单项选择对照。

## 已得到的结果

固定种子生成 1,000 条五赛季路线，得到 998 种可观察的人物与关系状态组合；64 条路线复跑完全一致；将一个选择替换为观察后，128 组对照有 85 组改变了后续状态。全部世界约束和剧情记录审计通过，六种剧情规则覆盖完整，九个固定场景通过。

第一轮实验还发现训练值会超过人物成长上限；修正规则后，同一批路线复测没有再出现违规。

这些数字代表结构化的模拟状态，不代表已写出 998 个完整、成熟的剧情文本。完整实验结论和限制见《大规模剧情分支工程验证记录》。

## 请设计师重点判断

1. 这种“人物目标 + 关系变化 + 事件规则”的结构，是否能作为项目的剧情系统参考？哪些部分值得保留？
2. 从玩家决定到人物变化再到后续事件，因果过程是否容易理解？哪些节点还缺少明确反馈？
3. 六类人物事件是否能构成可信的职业故事？人物动机、行为和结果之间是否有不自然之处？
4. 这套机制能否承载项目想表达的主题，还是会把人物简化成数值和条件？
5. 如果进入下一轮设计，最应该先补哪部分：人物个性差异、关系变化理由、长期记忆、事件文本，还是玩家介入方式？

可按“可直接参考 / 改造后参考 / 不建议参考”给整体判断，并指出最关键的 1–3 个理由。

## 文件清单与打开方式

- `outputs/world-model-engineering-bench.html`：可离线打开的单文件实验页面。按步骤推进到“核对赛果”，可以点击“自动跑 1000 条发展路线”查看批量验证结果。
- `outputs/large-scale-branch-validation-report.md`：实验方案、量化结果、修复记录和验证边界。
- `work/`：对应的规则、流程与 Chrome 浏览器检查脚本，供工程人员复核；设计评审无需运行这些脚本。

HTML 页面不依赖服务端或安装包，直接用浏览器打开即可。测试脚本从解压目录运行，例如 `node work/large-scale-branch-smoke.cjs`；浏览器检查脚本还需要 Chrome。原型没有实现完整电竞玩法、AI 对战或正式剧情文案；本包用于讨论剧情结构和系统参考价值。
